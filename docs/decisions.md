# auditoria-spring-boot-starter — Decisiones de implementación

Starter de la bandeja de salida (outbox) que embeben los productores de eventos de auditoría (Issuer, Verifier,
EBW…) para entregarlos a la [API de Auditoría](https://github.com/in2workspace/eudistack-core-audit). El diseño
es el [DT-002](https://github.com/in2workspace/eudistack-platform-dev/blob/main/docs/features/EUD-244-api-auditoria/DT-002-integracion-productores-auditoria.md)
de `eudistack-platform-dev/docs/features/EUD-244-api-auditoria/`.

Este documento no repite el diseño. Recoge las **decisiones tomadas al implementarlo** cuando el DT no cubre un
caso o no encaja con el código de los productores, y los **hallazgos** sobre el propio DT. Cada decisión respeta
el DT tal como está escrito. El Tech Lead las revisa cuando puede; si no está de acuerdo con alguna, se cambia
aquí y en el código. Mismo criterio que el
[`docs/architecture.md`](https://github.com/in2workspace/eudistack-core-audit/blob/main/docs/architecture.md) de la API.

## 1. Decisiones

| Id | Decisión | Origen |
|----|----------|--------|
| D-S1 | **Repositorio propio, `eudistack-platform-audit-starter`** (público, Apache 2.0), separado de la API. La API es un servicio que se despliega; el starter es una librería que se ejecuta dentro de cada productor, con otra cadencia de versiones. Los une solo el contrato (`openapi.yaml`) y el catálogo. Nombre según `repository-naming.md` (capa `platform`, recursos compartidos). | Confirmado por el Tech Lead. El DT no fija el repositorio; el diseño de la API y su `docs/architecture.md` dejan la bandeja de los productores fuera del servicio. |
| D-S2 | **Coordenadas `com.eudistack:auditoria-spring-boot-starter` y paquete raíz `com.eudistack.auditoria`**, como el DT. | DT-002 §1 y §3.2. Elegido frente a `net.eudistack`, que es el namespace de la otra librería de la organización (`eudistack-verifier-client-java`). Consecuencia en D-S3. |
| D-S3 | **Publicación solo en `mavenLocal`** (`./gradlew publishToMavenLocal`) por ahora. El repositorio remoto queda abierto: la otra librería de la organización publica en Maven Central bajo `net.eudistack`, y Maven Central solo admite un groupId de dominio verificado, que probablemente no es el caso de `com.eudistack`. Alternativa: GitHub Packages, que exige autenticación también para consumir. | Hueco del DT: "starter publicado" sin repositorio de artefactos. **[validar]** |
| D-S4 | **Dependencia base `spring-boot-starter`** y BOM de Boot 3.5.11 (la versión de los productores). Cada integración (R2DBC, JDBC, JPA, WebFlux, MVC, Spring Security, Micrometer) entra como dependencia opcional, para que un productor solo cargue la suya. | DT-002 AD-3 y AD-11. |
| D-S5 | **Interruptores apagados = ningún bean**, ni siquiera el de propiedades: la autoconfiguración entera se condiciona a `auditoria.publisher.enabled` o `auditoria.dispatcher.enabled`. Con uno encendido, la configuración se valida al arrancar (`source` con el publicador; `base-url` como origen sin path con el dispatcher; `lease` mayor que el timeout de lectura de 2 s). `batch-size` por encima de 100 se recorta a 100, no es un error. | DT-002 AD-8, §3.8 y §2.4. |
| D-S6 | **Contexto de una petición: filtro del starter + traductor del productor.** El starter registra un filtro (servlet) o `WebFilter` (reactivo) y gestiona el ciclo de vida del contexto. El productor aporta un bean `AuditContextResolver` / `ReactiveAuditContextResolver` que traduce `Authentication` (+ request) → `AuditContext`. La resolución es **perezosa**: se hace en el primer `stage` de la petición y se reutiliza, así que el orden de los filtros no importa. Si el resolver no da `correlation_id`, el starter genera uno por petición. | El DT (§3.3, §3.4.1, §3.8 paso 5) asume que los filtros existentes dejan `tenant`, `organization`, `correlation_id` y `actor`. Solo dejan el tenant (`TenantDomainWebFilter` en Issuer y EBW, `TenantDomainFilter` en Verifier), `correlation_id` no existe, y `actor`/`organization` salen de claims propios de cada servicio. El `TenantDomainWebFilter` del Issuer no declara orden. Implementado en B4 (D-S25…D-S27). |
| D-S7 | **`correlation_id` sobrescribible por el caso de uso** con `AuditContexts.withCorrelationId(id)` / `ReactorAuditContexts.withCorrelationId(id)`. | DT-002 §3.9.1: en una emisión es el id del proceso, que solo conoce el caso de uso. Implementado en B4. |
| D-S8 | **`Denied`/`Failure` con rollback del negocio: EC-09 sin cambios.** `stage` exige transacción activa y el starter nunca abre una. El productor captura el error fuera de la transacción de negocio y encola el evento en una transacción corta propia (`TransactionalOperator` / `TransactionTemplate`). Un `Success` va siempre en la transacción de negocio. No hay `stageStandalone`. | El DT no explica cómo sobrevive el evento al rollback (AD-6 asume que el aspecto toma el `reason` de la excepción). Detectado por el equipo de instrumentación. El patrón se prueba en B5; el comportamiento de `@AuditUseCase` en esos caminos se decide en B6. |
| D-S9 | **Token M2M: puerto `AuditAccessTokenProvider`** que implementa cada productor. El starter pide el token y lo refresca una vez en 401. | El DT habla del "puerto de credenciales de sistema que el productor ya use frente al Verifier". Ningún productor obtiene hoy tokens del Verifier como cliente. |
| D-S10 | **`auditoria.client.audience` opcional**: vacía, el dispatcher arranca con un WARN. | El DT la hace obligatoria con el dispatcher activo, pero la API no exige audiencia mientras el Verifier no la emita (D-16 de la API, PO-12; PA-03 del DT). |
| D-S11 | **PA-01 provisional: 10 aislamientos por ventana de 10 min**, configurables con `auditoria.dispatcher.quarantine-max-per-window` y `auditoria.dispatcher.quarantine-window` (esta segunda no figura en §3.8). **[validar N]** | DT-002 AD-9 y PA-01. |
| D-S12 | **Puertos y publicador duplicados por runtime**: `AuditPublisher` / `ReactiveAuditPublisher`, `AuditContextResolver` / `ReactiveAuditContextResolver`, `AuditAccessTokenProvider` / `ReactiveAuditAccessTokenProvider`. Reactor, Servlet, Spring Web y Spring Security son `compileOnly`: un productor servlet no carga Reactor ni al revés. Los puertos internos (bandeja, cliente HTTP, despertar) se definen en el bloque que los implementa (B2, B5, B7), no por adelantado. | DT-002 AD-3: un solo puerto reactivo obligaría al Verifier a cargar Reactor, y uno bloqueante obligaría a hacer `.block()` en WebFlux. |
| D-S13 | **`details` normalizado en el dominio** al construir el `AuditFact`: árbol inmutable de mapas, listas, textos, números y booleanos; los `null` se omiten en todos los niveles (paso 6), fechas e instantes pasan a ISO-8601 UTC y los UUID a texto. Un tipo no previsto (por ejemplo, un `enum`) se rechaza con la ruta y el tipo, nunca con el valor. `occurred_at` se trunca a milisegundos. | DT-002 §3.3 pasos 3, 4 y 6. Así la forma del JSON no depende de la configuración de Jackson de cada productor. |
| D-S14 | **JSON del payload escrito campo a campo con un `ObjectMapper` propio** (`AuditEventJson`), no con el del productor. Los opcionales ausentes se omiten; no hay `recorded_at`. Se valida contra `AuditEventInput` del OpenAPI con el mismo método que el `OpenApiContractIT` de la API. | DT-002 §3.3 paso 4. Una estrategia de nombres o de fechas del productor cambiaría el contrato sin que nadie lo note. |
| D-S15 | **Guardia de secretos** (`AuditDraftGuard`): claves **exactas** de una lista (`token`, `access_token`, `dpop`, `password`, `private_key`, `wia`, `pre_authorized_code`, `tx_code`, `client_secret`…), normalizando mayúsculas y separadores (`accessToken` → `access_token`), en `details` a cualquier profundidad; y **valores con forma de JWT** en `details`, actor, recurso y acción. El mensaje lleva la ruta, nunca el valor. | DT-002 §3.3 paso 5 y RQ-10. Exactas para no rechazar campos del catálogo como `secret_id` o `credential_configuration_id`. El valor con forma de JWT cubre un token colado bajo una clave inocente. |
| D-S16 | **El tiempo de la bandeja lo pone la base de datos.** Todas las sentencias usan `clock_timestamp()`; `reschedule` recibe un retraso (`Duration`), no una hora, y la base calcula `clock_timestamp() + retraso`. | DT-002 §3.7.3 ya usa `clock_timestamp()` en reclamación y reclaim. Con el reloj de cada pod, dos instancias desfasadas se contradirían en `next_attempt_at` y en el lease. |
| D-S17 | **El SQL de la bandeja vive en una sola clase de constantes** (`OutboxSql`) que usan los tres adaptadores, con parámetros con nombre y `CAST(... AS ...)` en vez de `::`. **`reschedule` y `quarantine` solo tocan filas `IN_FLIGHT` de la propia instancia** (`locked_by`); `delete` borra por `event_id` sin más condición, porque una fila que la API ha guardado se puede retirar sea quien sea su dueño. | DT-002 AD-3 ("el mismo SQL en los tres"). JPA necesita constantes para `@Query`, y Hibernate lee `::` como parámetro. La restricción por instancia evita que la respuesta tardía de un pod pise una fila que otro reclamó tras caducar el lease. Resuelve H-S2. |
| D-S18 | **El inicializador del esquema no hace nada si la tabla y su índice ya existen** (ni bloqueo ni DDL). Si faltan, toma `pg_advisory_xact_lock` y ejecuta el script en una transacción, con su propia conexión. | Varias instancias arrancando a la vez con `CREATE TABLE IF NOT EXISTS` pueden chocar en PostgreSQL. Desde PostgreSQL 15 el usuario de la aplicación puede no tener `CREATE` en `public`: una vez provisionada la tabla, el servicio arranca igual (R-8, PA-05). |
| D-S19 | **El store JDBC solo se activa en aplicaciones servlet** (`@ConditionalOnWebApplication(SERVLET)`), con `DataSource` y sin otro `OutboxStore` registrado. | Resuelve EC-14 por el tipo de aplicación: el Issuer es reactivo y nunca acaba en JDBC aunque tenga el driver de Flyway. El orden frente a JPA, en D-S23. |
| D-S20 | **`stats()` devuelve una sola instantánea** (pendientes, en cuarentena, edad del más antiguo) en lugar de los tres métodos de §3.4.1 (`countPending`, `countQuarantined`, `oldestPendingAge`). | Una consulta en lugar de tres para cada lectura de los gauges y del health indicator. |
| D-S21 | **Puerto `ReactiveOutboxStore` y `R2dbcOutboxStore`** con las mismas operaciones en `Mono` y el mismo SQL; un argumento inválido es una señal de error, no una excepción al construir el `Mono`. **El esquema de un productor reactivo se crea por R2DBC** (`R2dbcAuditOutboxSchema`), con el mismo comportamiento que el de JDBC (D-S18), y se espera su resultado solo al arrancar. | DT-002 AD-3. Un productor reactivo puede no tener `DataSource` (el Issuer desactiva el de Flyway). Esperar en el arranque no toca el camino de negocio, que es lo que prohíbe AD-3. |
| D-S22 | **JPA con `EntityManager` y consultas nativas**, sin repositorio de Spring Data ni `@Entity`. Las operaciones del dispatcher abren su propia transacción (`REQUIRES_NEW`); el insert se une a la de negocio y, sin ella, JPA lo rechaza (`TransactionRequiredException`). | El DT pide "`@Query` nativa", pero un repositorio de Spring Data exige una entidad, y R-4 prohíbe mapear la bandeja. JPA exige transacción para `UPDATE` y `DELETE`, y la propia los confirma antes del HTTP (AD-4). |
| D-S23 | **Selección del store por tipo de aplicación y orden de autoconfiguración**: reactiva → R2DBC; servlet con JPA → JPA, evaluada antes que JDBC (una aplicación JPA siempre tiene también `DataSource`); servlet sin JPA → JDBC. La tabla se crea por JDBC también en la aplicación JPA. | Tabla de selección de DT-002 §3.4.1 y EC-14. Probado en `AuditOutboxStoreSelectionIT`. |
| D-S24 | **Parámetros de texto anulables con `CAST(... AS varchar)`** en el SQL compartido (`traceparent`, `last_error`, `quarantine_reason`). Las comprobaciones de argumentos de las operaciones viven en `OutboxArguments`, comunes a los tres stores. | En una consulta nativa, Hibernate no sabe qué tipo dar a un `null` sin tipo. Así los tres adaptadores rechazan lo mismo de la misma forma. |
| D-S25 | **El contexto vive en el paquete `context`, con una API por runtime**: `AuditContexts` (hilo actual, devuelve un `AuditContextScope` para try-with-resources) y `ReactorAuditContexts` (Reactor Context, devuelve una función para `contextWrite`). Puertos de lectura `AuditContextAccessor` y `ReactiveAuditContextAccessor`. | El DT pone `AuditContexts` en el dominio con una sola API. Pero un `ThreadLocal` y el Reactor Context son mecanismos, no dominio, y una API única obligaría a cargar Reactor en el Verifier (D-S12). |
| D-S26 | **Alcances apilados y perezosos.** En el hilo, cada alcance abre un marco que se cierra en orden inverso (cerrar fuera de orden lanza `IllegalStateException`) y restaura el anterior. El contexto de una petición se resuelve una sola vez, en la primera lectura, y se reutiliza: el `correlation_id` generado es el mismo para todos los eventos de la petición. `withCorrelationId` deriva del contexto de debajo; si no hay ninguno, sigue sin haberlo. Un `system` sin `correlation_id` genera uno al abrirse (en reactivo, en cada suscripción). | AD-10 ("o uno nuevo creado al abrir el alcance") y RQ-09 (un `correlation_id` común a la operación). El cierre estricto evita que un alcance mal cerrado deje el contexto de otro tenant puesto en el hilo. |
| D-S27 | **Qué se registra según el productor**: una aplicación reactiva tiene el accessor del Reactor Context; cualquier otra (servlet o sin web), el del hilo. El filtro de petición solo se registra si el productor declara su resolver y tiene Spring Security; sin él, solo funcionan los alcances explícitos. | Un proceso de segundo plano sin web también necesita `AuditContexts.system`. Sin resolver no hay forma de saber el contexto de una petición, y es mejor que `stage` falle con un error claro que inventarlo. |

## 2. Hallazgos sobre el DT-002

| Id | Hallazgo | Propuesta |
|----|----------|-----------|
| H-S1 | La matriz de tests de §2.3 repite filas (RQ-21…RQ-26), y `OutboxPoisonBatchIT` y `OutboxShutdownReleaseIT` figuran como *Unit* aunque su nombre es de integración. | Se implementan según lo que prueban: los que necesitan PostgreSQL, como IT. |
| H-S2 | §3.7.3 da el SQL de reclamación, reclaim, liberación y cuarentena, pero no el de borrado ni el de reprogramación. | Resuelto en D-S17. |
| H-S3 | El Verifier no tiene ninguna transacción local (`@Transactional`, `TransactionTemplate`), y `stage` la exige (EC-09). | Afecta a la instrumentación del Verifier, no al starter. |
| H-S4 | `payload` es `JSONB` (§3.7.3), y PostgreSQL no conserva el texto: reordena las claves y quita los espacios. El dispatcher envía la forma de `JSONB`, no la cadena que escribió `stage`. | Sin efecto: el contenido es el mismo y la API calcula la idempotencia con JSON canónico (RFC 8785, `IdempotencyPolicy`), así que un reenvío sigue siendo `duplicate`. Si algún día hiciera falta el texto exacto, la columna tendría que ser `TEXT`. |
